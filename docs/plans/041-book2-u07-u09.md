## Governing principle & the lesson-solver rule

**User (2026-09-10): enough worked examples for genuine mastery — NO learning-duration constraint.**
`judge-check` expects `l1..l{manifest.lessons}` ∪ referenced `assets/lN.py`: **U07 → `l1`,`l2`**

`solve()` becomes `lN`; the other demos become executable literal-data rungs. `lessons` and the
coverage-map stay unchanged (advisory).

**Contract-transform recipe (proven, plans 039/040):** read the ORIGINAL `solve()` from a pre-migration
git ref; drop `def solve`, `dedent`, convert ONLY the solver's OWN top-level `return X`→`print(X)`
(AST-scoped, so a NESTED recursive helper's returns are untouched); prepend `import sys` /
`data = sys.stdin.read()`. Cases the recipe must cover, by number of `solve()`-OWN top-level returns:
- **one** (single final return) → mechanical `return X`→`print(X)`.
- **two, mutually exclusive** (guard `if c: return A` then `return B`) → explicit `if/else`, one `print`
  per branch.
- **three or more, mutually exclusive** (e.g. **U07 ex7** `ALI`/`BO`/`TIE`, `solutions.ipynb` cell 14)
  → hand-write an `if/elif/else` chain with exactly ONE `print` per branch. A naive per-`return`
  `print` would emit twice on the early paths, so these are hand-written (as U03 ex5 was in plan 040).
- **early return inside a loop** (binary/complete search) → the I/O-preserving found-flag form.

Both U07/U09 *designated lesson* solvers wrap their body in an outer `solve()` whose OWN return is the
single final one (recursion lives in a nested helper), so they transform mechanically; the multi-return
case is confined to a few `exN`. **Before Phase A, run a top-level-return count over all 18 `exN`
solvers and hand-write any with a guard chain (>1 mutually-exclusive return) or a loop return.** Verify
every solver by subprocess before commit.

## U07 — Simulation & Ad Hoc (introduces `simulation`; lessons:2)

- **L1 — model the state, apply every rule in order.** THREE FRESH one-increment executable rungs
  (fresh literal data, distinct from any exercise sample and from `l1`), each a Notice: (1) parse the
  initial state from a literal input and print it; (2) apply ONE rule to the state (e.g. a capped
  increment `min(cap, value+delta)`) and print; (3) apply a SEQUENCE of rules in a loop over literal
  commands, printing the running state. Then **Put it together** `l1.py` = the capped battery-state
  solver (lesson cell 3), `no-exec` + run line + complexity `O(steps)`. **Use fresh `l1` sample data —
  the shipped cell-3 sample is token-identical to Exercise 2's, so craft new numbers for `l1/1.in`
  (glm-N3).**
- **L2 — edges & provable termination.** THREE FRESH rungs: (1) an edge case at a boundary (clamp /
  wrap guarded); (2) a loop with an explicit stop condition that provably terminates; (3) a
  step-cap / already-seen-state check so an ad-hoc loop cannot run forever — **track seen states with a
  LIST + `in` or a plain step counter, NOT a set (`set-literal`/`set-ops` are U04 features, untaught in
  U07 → would RED concept-scan; glm-N5)**. Then **Put it together** `l2.py` = the terminating
  event-walk solver (lesson cell 8; **use fresh `l2/1.in`, distinct from Exercise 3's sample**),
  `no-exec` + run line + complexity. (Lesson **cell 6 is the grid-move robot solver** — NOT the
  "edge-light automaton", which is Exercise 6; cell 6 becomes an L2 rung, described accurately.)
- **Closure:** introduces `simulation` (technique); requires control-flow/list/dict/int/print; no new
  feature (no set/comprehension/banned construct — U07's union is unchanged from `main`).

## U09 — Recursion & Backtracking (introduces `recursion, backtracking`; lessons:3)

Each `lN` mirror is the pinned solver; the rungs are FRESH literal-data cells (distinct data), so a
cell is never both a live rung and its `no-exec` mirror (glm-N1).

- **L1 — a function solving a smaller copy (recursion).** THREE fresh rungs: (1) **factorial** (base
  case `n==0/1` → recursive case) on a literal n (from cell 2's shape); (2) **countdown** printing
  during the unwinding to show the call stack (cell 5's shape); (3) a small **recursive sum** of `1..n`
  on literal data. Then **Put it together** `l1.py` = the recursive-sum stdin solver (cell 4), on FRESH
  sample data, `no-exec` + run line + complexity `O(n)` depth.
- **L2 — try, recurse, undo (backtracking).** THREE fresh rungs: (1) **include-or-skip subsets**
  counting those hitting a target (`path + [value]`); (2) **permutations under a spacing constraint** —
  choosing an unused value with a `used` list toggled/restored AND rejecting a choice whose value is
  within 1 of the previous (cell 10 is `abs(path[-1] - choice) >= 2` — describe THIS, not plain
  permutations; glm-N1/fable-3); (3) **combinations** choosing in increasing index order. Then **Put it
  together** `l2.py` = the subset-count stdin solver (cell 8), on FRESH data, `no-exec` + run line +
  complexity note (exponential — small N). NO `.pop`; undo via `used[i] = False` / fresh `path +
  [value]`.
- **L3 — parsing a nested structure by recursion.** THREE fresh rungs building toward recursive
  descent: (1) evaluate a single literal token; (2) evaluate one nested level; (3) recurse into
  arbitrary nesting. Then **Put it together** `l3.py` = the nested-expression evaluator (cell 14), on
  FRESH data, `no-exec` + run line + complexity.
- **Closure:** introduces recursion (FEATURE — confirm USED via `detect()`) + backtracking (technique);
  requires control-flow/list/int/str/print; NO `.pop`, no comprehension, no lambda; recursion is legal
  here.
