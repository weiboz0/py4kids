## Governing principle & the lesson-solver rule

**User (2026-09-10): enough worked examples for genuine mastery — NO learning-duration constraint.**
`judge-check` derives expected lesson PIDs as `l1..l{manifest.lessons}` ∪ the lesson's `assets/lN.py`

**U04 → `l1`,`l2`** (lessons:2), **U05 → `l1`,`l2`,`l3`** (lessons:3). Where a lesson currently has

coverage-map stay unchanged (advisory).

## Closure discipline (preserve what each unit already teaches)

The migration must NOT introduce constructs a unit hasn't taught. Ladder rungs use ONLY the operations
the shipped solvers already use. Per-unit reminders (from the concept-scan authoring history):

- **U03 Complexity** introduces technique `complexity`. Rungs count operations / tabulate growth /
  read constraints — plain loops, `len`, arithmetic, `range`. No new feature.
- **U04 Sets/Tuples/Sorting** introduces FEATURES `set-literal`, `set-ops`, `tuple`, `sorted-key`.
  Set-ops ONLY via `.add`/`.discard` on a `{…}`/`set()` var **in the same cell**, and/or `set_a - set_b`
  (ast.Sub). **NEVER `& | ^` on sets** (fires `bitwise-ops`, untaught till U11). **NEVER
  `.union`/`.intersection`/`.difference`** (untaught methods → concept-scan RED) — build them with a
  loop + `.add`. `sorted-key` = `sorted(seq, key=named_fn)` with a NAMED function, **no lambda**
  (`ast.Lambda` is banned by source-policy). Tuples via literal/unpack/`return (a,b)`.
- **U05 Searching/Complete-search** introduces techniques `binary-search`, `complete-search`. Plain
  while/for loops, `lo/hi/mid`, nested loops for enumeration. No new feature; recursion is NOT used
  (untaught till U09 — complete search here is iterative/bitmask-free per the shipped content).
- **All units:** allowed builtins are the pinned source-policy set
  `{len,min,max,sorted,sum,abs,round,input,print,range,int,str,set}` — so `all/any/enumerate/zip/
  reversed` stay banned; no `+=`/AugAssign, no chained compare, no `[x]*n` repetition, no comprehension,
  no ternary `IfExp`, no `.pop/.join/.index/.count/.find`, no `global/nonlocal/del`. The shipped solvers
  already satisfy this; AST-verify after transform.

## U03 — Complexity (introduces `complexity`)

The current lesson is already ladder-shaped (Count the Operations → Three Growth Families → Read the
Constraints → Halve a Number Range → One Problem, Two Approaches → A Contest Checklist). Keep that spine;
make the early cells **executable literal-data rungs** with a `**Notice:**` each, and end on a stdin
solver.

- **L1 — choose an algorithm that fits the constraints.** Rungs (≥3, executable on literal data):
  (1) **Count the Operations** — two snippets over a literal list, print the operation count so the
  O(n) vs O(n²) gap is concrete; (2) **Three Growth Families** — print `n`, `n²`, `2ⁿ` for
  `n ∈ {10,100,1000}` so the student SEES which blows past a ~10⁸ budget; (3) **Read the Constraints**
  — from a literal `n` and a budget, decide which family is affordable (print the verdict);
  (4) **Halve a Number Range** — the binary-halving op-count on a literal range (counts ≈ log₂ n).
  Then a **counterexample rung**: the O(n²) "slow approach" from *One Problem, Two Approaches* run on a
  literal input, printing its operation count to show it exceeds budget at the stated constraints —
  motivating the fast one. **Put it together** `l1.py` = the FAST (linear/`O(n)`) approach of the two,
  transformed to a stdin solver, shown `no-exec` + run line + complexity note contrasting the two
  approaches. (The slow approach stays an executable demo rung, NOT a judged solver.)
- **Closure:** introduces `complexity` (technique, reviewer-enforced); requires the Book-1 control-flow/
  int/list/print concepts the rungs use; no new feature, no banned construct.

## U04 — Sets, Tuples & Sorting (introduces `set-literal, set-ops, tuple, sorted-key`)

Two lessons. Convert the per-section `def solve` demos into graduated rungs; end each lesson on a stdin
solver.

- **L1 — sets (distinct, membership, set operations).** THREE one-increment executable rungs:
  (1) build a set from a literal list of values and print `len(s)` (distinct count) — introduces the
  `{…}`/`set()` literal; (2) membership — test `x in s` for a few literal `x`, print hits; (3) combine
  two literal sets into their intersection/difference with a **loop + `.add`** (and/or `set_a - set_b`),
  printing the result — NO `& | ^`, NO `.union`/`.intersection`/`.difference`. Then **Put it together**
  `l1.py` = the representative set stdin solver from L1's material (e.g. count distinct / common
  members), `no-exec` + run line + complexity (`O(n)` set build + membership).
- **L2 — tuples & sorting by a chosen field.** THREE one-increment executable rungs: (1) pack records
  as tuples in a literal list and index a field; (2) `sorted(records, key=field_of)` by ONE field with
  a NAMED key function (no lambda), print the order; (3) compound key — a named function returning a
  `(primary, secondary)` tuple, print the tie-broken order. Then **Put it together** `l2.py` = the
  sort-by-field stdin solver (named key), `no-exec` + run line + complexity (`O(n log n)`).
- **Closure:** union introduces set-literal/set-ops/tuple/sorted-key (all FEATURES — confirm each is
  USED via an ad-hoc `detect()` run); requires the parsing/control-flow prereqs; `sorted`/`set`/`len`
  are allowed builtins. No `& | ^` on sets, no lambda, no untaught set methods.

## U05 — Searching & Complete Search (introduces `binary-search, complete-search`)

Three lessons, already split (Lesson 1 linear→binary→lower-bound; Lesson 2 complete search; Lesson 3
search over the answer). One stdin solver per lesson.

- **L1 — searching a sorted list.** THREE rungs: (1) **linear search** a literal list, print the found
  index (the baseline, `O(n)`); (2) **binary search** the same SORTED literal list with an explicit
  `lo/hi/mid` loop, print the index — contrast the step count with L1-rung-1; (3) **lower bound** —
  turn the search into counting "how many ≤ x" on a literal sorted list. Then **Put it together**
  `l1.py` = the binary-search stdin solver, `no-exec` + run line + complexity `O(log n)`.
- **L2 — complete search (try every allowed choice).** THREE rungs: (1) enumerate all pairs `(i,j)`
  over a tiny literal list with nested loops, print each; (2) count the pairs meeting a condition;
  (3) track the best over all choices (running best, no early structure). Then **Put it together**
  `l2.py` = the complete-search stdin solver, `no-exec` + run line + complexity (e.g. `O(n²)`) + a note
  that this is only affordable because constraints are small (ties back to U03).
- **L3 — search over the answer.** THREE rungs: (1) a `feasible(candidate)` check on literal data for a
  FIXED candidate, print yes/no; (2) scan candidates linearly to find the boundary, print it;
  (3) binary-search the candidate range using `feasible`, print the answer. Then **Put it together**
  `l3.py` = the search-over-answer stdin solver, `no-exec` + run line + complexity
  `O(n log(range))`.
- **Closure:** union introduces binary-search/complete-search (techniques, reviewer-enforced); requires
  control-flow/int/list/while/print; no recursion (untaught till U09); allowed builtins only.

prepend `import sys` / `data = sys.stdin.read()`), PLUS `ex1`–`ex9` from each shipped `solutions.ipynb`.
Each solver ships **≥2 NON-VACUOUS** `.in`/`.out` fixtures derived from the shipped asserts (+ crafted
where a lesson solver needs a 2nd). **Verify every solver against every fixture by subprocess BEFORE
committing.**

**Per-unit mutation witnesses (name one killing fixture each — the content gate WILL mutation-test):**
- **U03 `l1`** (fast vs slow): a fixture whose answer the O(n²) mutant would get wrong only if the
  decisive value is positioned to defeat a prefix/drop-last bug (decisive-LAST input).
- **U04 `l1`** (sets): a fixture with DUPLICATES so a "skip set / use list" mutant miscounts distinct;
  **`l2`** (sort): an UNSORTED input whose answer changes if the `sorted(key=…)` call is dropped, plus a
  TIE so a missing compound-key tiebreak is caught.
- **U05 `l1`** (binary search): a target present ONLY at the last/boundary slot (kills a `hi=n-1` vs `n`
  / `lo<hi` vs `<=` off-by-one); **`l2`** (complete search): a self-pair case `(i==j)` so a missing
  `j>i`/`j!=i` guard fails; **`l3`** (search-over-answer): an input where the feasible boundary is at
  the range edge (kills a `lo`/`hi` initialization off-by-one).
