## Governing principle & the lesson-solver rule

**User (2026-09-10): enough worked examples for genuine mastery — NO learning-duration constraint.**
`judge-check` derives expected lesson PIDs as `l1..l{manifest.lessons}` ∪ the lesson's `assets/lN.py`
references: **U03 → `l1`** (lessons:1), **U04 → `l1`,`l2`** (lessons:2), **U05 → `l1`,`l2`,`l3`**
(lessons:3). Each `lN` is pinned below to an EXACT current lesson cell; non-representative `def solve`
demos become executable literal-data rungs leading up to it. `lessons` and the coverage-map stay
unchanged (advisory).

**Contract-transform vs logic change (reconciles "Out of scope"):** converting a `solve()` that
`return`s into a top-level script that `print`s is the stdin contract transform, not a logic change. For
a straight-line solver it is the proven mechanical recipe (drop `def solve`, `dedent`, convert the
solver's own top-level `return X`→`print(X)`, prepend `import sys` / `data = sys.stdin.read()`). Four
U05 lesson solvers (`l1` binary search, `l2` pair search, and their sibling demos) `return` EARLY from
inside a loop; for those the transform uses the **semantics-preserving found-flag idiom already used by
the shipped U05 EXERCISE solvers** (`answer = "NO"` / set it / `break` or guard the loop with
`and answer == "NO"`, then `print(answer)`) — identical input→output, restructured control flow only.
Phase A's mandatory subprocess verification (pristine output must match the shipped assert) catches any
botched transform. Most `ex1`–`ex9` solvers are straight-line, but any solver with two top-level
mutually-exclusive returns (e.g. **U03 ex5** = `solutions.ipynb` cell 9: `if found: return "YES"` then
`return "NO"`) needs an explicit `if/else` (or the found-flag form) so exactly one `print` fires — do
NOT assume every ex solver is purely mechanical.

## Closure discipline (preserve what each unit already teaches)

Ladder rungs use ONLY operations the unit already teaches (the shipped solvers are closure-clean on
`main`; the transform introduces no new construct). Per-unit reminders from the concept-scan history:

- **U03 Complexity** (introduces technique `complexity`): rungs count operations / tabulate growth /
  read constraints using plain loops, `len`, **multiplication** (`n * n`), and `range`. **No `**`/`pow`
  (untaught in Book 1, and `ast.Pow` maps to the taught `arithmetic` concept so concept-scan would NOT
  catch it — reviewer-enforced).** The existing growth demo already uses `n * n` and never shows 2ⁿ —
  keep it that way. The O(n²)-at-large-N cost is shown as an ARITHMETIC ESTIMATE (`large_n * large_n`,

  `needed in seen`) — dict-access is already in U03's shipped requires/practices on `main`; preserved.
- **U04 Sets/Tuples/Sorting** (introduces FEATURES `set-literal`, `set-ops`, `tuple`, `sorted-key`):
  set-ops ONLY via `.add`/`.discard` on a `{…}`/`set()` var **in the same cell**, and/or `set_a - set_b`
  (`ast.Sub`). **NEVER `& | ^` on sets** (concept-scan's `visit_BinOp` fires `bitwise-ops`, untaught
  till U11 → RED; `source-policy` does NOT catch this — concept-scan does). **NEVER
  `.union`/`.intersection`/`.difference`** (not in `taught_methods` → concept-scan "untaught method"
  RED) — build them with a loop + `.add`. `sorted-key` = `sorted(seq, key=named_fn)` with a NAMED
  function, **no lambda** (`ast.Lambda` banned by source-policy). Tuples via literal/unpack/`return
  (a,b)`. **Judged/printed output stays numeric counts or names (never raw set contents)** so `.out`
  fixtures are deterministic under per-subprocess string-hash randomization (the shipped solvers already
  print counts/names).
- **U05 Searching/Complete-search** (introduces techniques `binary-search`, `complete-search`): plain
  while/for loops, `lo/hi/mid`, nested loops. **No recursion** (untaught till U09; `recursion` is

## U05 — Searching & Complete Search (introduces `binary-search, complete-search`; lessons:3)

Three lessons already split. One stdin solver per lesson, pinned to a cell. `l1`/`l2` need the

- **L1 — searching a sorted list.** Rungs: (1) **linear search** a literal list, print the found index
  (baseline `O(n)`); (2) **binary search** the same SORTED literal list with an explicit `lo/hi/mid`
  loop (found-flag form), print the result, contrast the step count with rung 1; (3) **lower bound** —
  count "how many EQUAL x" on a literal sorted list (cell 6 computes `lower_bound(x+1) - lower_bound(x)`
  — copy the cell's actual logic, not a "≤ x" paraphrase). Then **Put it together** `l1.py` = **cell 4**
  (binary search), found-flag transform, `no-exec` + run line + complexity `O(log n)`. Witness: target
  present ONLY at the last/boundary slot so a `lo < hi` vs `lo <= hi` off-by-one fails (it misses the
  final single-element check). (Note — sol: a `hi = n` mutant is an alternative-convention
  out-of-bounds error, not killed by this one fixture; treat it as reviewer/AST-caught, don't claim the
  boundary fixture kills every index mutation.)
- **L2 — complete search (try every allowed choice).** Rungs: (1) enumerate all pairs `(i,j)`,
  `j>i`, over a tiny literal list, print each; (2) count pairs meeting a condition; (3) the **triple**
  escalation — nested-×3 enumeration (cell 10) with its O(n³) note, shown as a rung (NOT retired — sol/
  glm). Then **Put it together** `l2.py` = **cell 8** (the PAIR two-sum complete search), found-flag
  transform, `no-exec` + run line + complexity `O(n²)` + a note that it's only affordable because
  constraints are small (ties back to U03). Witness: a self-pair case — target `= 2·v` for some single
  value `v` with NO distinct pair summing to target, so a mutant using `range(n)` (allowing `j==i`)
  wrongly prints `YES` while the pristine `range(first+1, n)` prints `NO`.
- **L3 — search over the answer.** Rungs: (1) a `feasible(candidate)` check on literal data for a FIXED
  candidate, print yes/no; (2) scan candidates to find the boundary; (3) binary-search the candidate
  range using `feasible` (cell 12). Then **Put it together** `l3.py` = **cell 12** (ship-loading
  capacity search; single final `return` — straight mechanical transform), `no-exec` + run line +
  complexity `O(n log(range))`. Witness: a **`D = 1`** (one day) fixture whose answer is `sum(weights)`,
  e.g. `"3 1\n5 2 7"` → `14`, which a `hi = sum - 1` initialization mutant cannot reach (prints ≤13) —
  plus the shipped `"5 3 4 2 7 3 9"` → `10`. Use fresh L3 sample data distinct from Exercise 7, and
  number that fresh fixture `l3/1.in` (the lesson run line shows `< assets/l3/1.in`, so `1.in` must be
  the fresh sample, not ex7's — fable).
- **Closure:** union introduces binary-search/complete-search (techniques, reviewer-enforced); requires
  control-flow/int/list/while/print; no recursion; allowed builtins only.
